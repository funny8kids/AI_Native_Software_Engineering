- **（2026-09-24）居中 flex 遇上超宽子元素 = 滚不回来的左溢出**：`.mermaid` 是 `justify-content:center` 的 flex，子 `svg` 比滚动容器宽时，居中把左半张推到容器左侧之外，而 `scrollLeft` 不能为负——实测图左缘 x=-216（容器左缘 24），**左半张永久丢失且没有任何报错**。修法是在窄屏改 `justify-content:flex-start`。这类缺陷命中测试看不见（图不在点击清单里），只能靠几何闸量「viewBox 宽 / 渲染宽 / 左缘」。
- **（2026-09-24）本站真正的横向滚动容器是 `.content`，不是 `documentElement`**：第六条守卫第一次做变异自检时，「正文强行加宽到 1400px」这条变异**零报红**——因为判据量的是 `documentElement.scrollWidth - innerWidth`，实测恒为 0，而破版实际发生在 `.content`（绝对定位的滚动层）里。补上 `contentEl.scrollWidth - clientWidth` 后同一变异立刻报红「正文层 .content 横向溢出 1010px」。教训：**判据量错盒 = 一条永远绿的闸**；每条溢出类判据要写清它量的是哪个滚动容器，并用变异证明那个容器确实是读者看到破版的那一个。
- **（2026-09-24）第六条守卫 `check_mobile.py`（窄屏几何闸）与其五条变异**：命中测试看不见"折行"和"缩糊"——顶栏链接 `rect` 高 59、中心 y=29 全在 60px 条内，命中测试全绿，读者看到的却是两行挤在一起的半截字。所以几何判据独立成闸：顶栏单行且在条内、每张 mermaid 缩放 ≥0.95、图左缘不越容器、`.content` 与文档均无横滚。变异 A（去 `nowrap`）→「跑出固定条」20 条、B（可压扁）→「折成 2 行」20 条、C（撤掉宽图左对齐）→「居中溢出滚不回来」6 条、D（强撑正文）→「正文层 .content 横向溢出」4 条、E（定宽守卫失配）→「等比缩成糊图」5 条，退出码 0。变异 C 的锚**必须是两条规则一起删**：`.is-wide` 那条与 `@media (max-width:768px)` 里那条是同一机制的两半（桌面靠挂号、窄屏靠媒体查询），只删一条时另一半原地生效，读数为 0 红——"一条判据为什么没红"要先问"是不是还有一份代码在替它顶班"。
- **（2026-09-24）变异锚点必须唯一：`replace(old, new, 1)` 只吃第一处**：上面那条 E 第一次跑是**未被捕获**（守卫判 0 条报红）。原因不在判据，而在变异本身：锚点 `window.matchMedia('(max-width: 768px)')` 在 `index.html` 里有两处，`count=1` 的替换打到了前一处 `ainseGanttWidth()` 上，窄屏定宽守卫原地不动，图当然不糊。这类"假自检失败"比假绿更难发现，因为它看起来像在指责判据太松。修法：锚点写成整行以消歧，并让 `apply_mutation` 在 `text.count(old) != 1` 时**中止并报名**——歧义要在打补丁之前死掉，而不是靠读数反推。
- **（2026-09-24）探针自身还会撒三个谎（都表现为"验证通过"）**：① 拼 URL 时留下双斜杠，请求 404 但页面照样渲染完，读数一切正常；② 读颜色时丢掉 alpha 通道，`rgba(255,255,255,0)` 被当成纯白通过了对比度判据；③ 用 `localStorage` 直接写主题键再刷新来"验证深色模式"——那绕过了 `#btn-theme` 的真实点击路径，按钮坏了也能全绿。此后主题类结论只认真点按钮后的读数（第五条守卫的 `click_chain` 即按此写）。
- **（2026-09-24）选择器匹配不到节点时"0 失败"是空集，不是通过**：一次视觉探针用 `.part-num` 量部分卷首编号，返回 0 处问题——真相是该类名在渲染结果里根本不存在（页面上没有任何节点被量到）。守卫此后必须**自报覆盖集**（量了几个、什么选择器），空集要显式报"零覆盖"而不是绿。同理，`elementFromPoint` 在视口外返回 `null` 属于"不可测"，不得计入"点不动"——390 顶栏第 5 项「搜索」中心点在横滚区外，按 offscreen 跳过并写明，改点中心点恒在屏内的第 3 项。
- **（2026-09-24）`docs/README.md` 总览页上原样显示出一条 `---`**：`<div>` 起的 HTML 块要遇到**空行**才结束，紧跟标签行的 `---` 被当作字面量渲染。这类破损不报错、不影响死链、DOM 里也"看得见"，因此补进第三条守卫 `check_markdown.py`：上一行是 HTML 标签行、本行是 `---`/`#`/`>`/表格/列表且中间没有空行 → 报红。
- **（2026-09-24）窄屏宽表用 `display:block` 换滚动，是把表格语义换成了可视滚动**：`@media (max-width:768px)` 里过去写 `table{display:block; overflow-x:auto}`——读者能滚，但 `display:block` 会把 `<table>` 从可访问性树里抹掉（读屏不再报行/列，`cols/rows` 结构消失）。改成渲染层挂号：`index.html` 的 `tableScroll` 插件在 `afterEach` 给每个 `<table>` 套一层 `.table-scroll`（滚动交给它），表格自己保持 `display:table`。实测（390 与 1280 各 4 页）：`display=table`、父层 `table-scroll`、`overflow-x:auto`；390 下 21 张表有 9 张需要滚动（最宽溢出 277px），1280 下 0 张；`.content` 与文档横向溢出仍为 0。
- **（2026-09-24）"溢出"判据必须区分「滚出正文列」和「被滚动容器接住」**：加了包裹层后，视觉探针在 390 报了 10 处"溢出内容区"（表格页 6 处）。逐条查：报的都是 `.table-scroll` 内部按内容撑开的表格，容器本身贴齐正文列、`.content` 读数为 0——是判据没建模滚动容器，不是破版。修法是给豁免加条件（祖先里确有 `overflow-x:auto/scroll` 且**该祖先自己**在正文列内），并且**豁免只对后代生效、容器自身仍被检查**（`.table-scroll` 已加进被检选择器）。独立支撑来自另一条守卫：第六条守卫健量 `.content` 与文档的横滚，且它的变异 D 证明这条读数会报红——不是把缺陷改名成特性。
- **（2026-09-24）会打印失败却退出码 0 的探针，本身就是一条假闸**：上述 4 页报红的那一轮，脚本 `rc` 仍是 0（它只打印不判分）。这等于给读者发"全绿"的假凭据。修法：把每页的 `fails` 存进 `report`，末尾按 `失败/作废` 条数给退出码。此后任何探针脚本进复核链之前，先问一句"它红的时候退出码是几"。
- **（2026-09-24）可读性地板：桌面档才是主战场，窄屏定宽常量解决不了它**：390 档修好之后重测 1280，41 张图缩放仍 <0.85，最差是案例四 ch37 的 `viewBox` 宽 1491 → 渲染 638px（缩放 0.428），节点「CTO 阿坤」有效字号 6.85px，全站 15 张图低于 11px。根因是先前那条定宽只挂在 `@media (max-width:768px)` 上，而正文栏在 1280 也只有 638px——**"窄"是相对正文栏的，不是相对视口的**。修法改成逐图求解：`有效字号 = 节点自然字号 × 渲染缩放`，要让地板 ≥11px 就需要 `min-width = viewBox宽 × 自然字号 / 11`，超出正文栏的部分交给 `.mermaid-block` 横向滚动，同时给该图宿主挂 `.is-wide` 改左对齐（居中 flex 会把左半张推到 `scrollLeft` 滚不回的负偏移）。**不用 CSS 定值**：定值会把 302px 的甘特也拉到 600px（缩放 2.0，字号失控），这条先前踩过一次。
- **（2026-09-24）滚动暗示层要挂在「不滚动」的容器外面**：实测全站需要横向滚动的容器 352 处、视觉暗示覆盖率 0——读者在 390 档面对的是一张溢出 1167px 的图，界面上没有任何一处说"还能往右滚"。做法是给每个滚动容器套一层 `.scroll-frame`（**不滚动**的那一层），左右各挂一片 `.scroll-veil`：`mask-image` 做渐隐、`::after` 用内联 SVG 遮罩画方向箭头、`pointer-events:none`、状态类 `has-left/has-right` 由 `scroll`/`resize` 同步。两条容易忽略的：① 渐隐伪元素若挂在**滚动容器自己**身上，它会跟着内容一起滚走，暗示在滚的第一帧就消失；② 渐隐的底色要按层选——表格压在页面底色上、图有自己的卡底，用 `--c-veil` 分开给（图那层用 `--c-bg-soft`，否则边缘露出一条白边）。`pointer-events` 不是可选项：它压着的就是图节点与表格单元格，第七道守卫在右缘逐点做 `elementFromPoint` 命中测试。
- **（2026-09-24）「该不该显示」只问状态类，不问 computed opacity，也不问量测时的坐标**：交互闸把暗示层纳入真实点击清单后，连续两轮报"候选 0 处"——判据一次都没执行，而"没执行的判据"和"通过的判据"输出完全一样。第一版用 `getComputedStyle().opacity` 当条件：与滚动/换类同一次求值里读到的是 `.18s` 渐变的**起始值**，永远读不到 1。第二版改用"坐标在视口内"筛候选：同样 0 次真点，因为坐标是在同一次求值里量的，而控件那段之前调过 `settle()` 滚过侧边栏，正文里暗示层的 y 已经换人（实测 ch37 那条 y=7345，远超 900 视口）。终版只交**状态类 + 容器序号**，真点前按序号重新定位、重新量坐标，并补一条硬失败：「命中测试量到 N 点、该侧有状态类 M 点，真实点击却 0 次 ⇒ 本档结论不成立」。教训：**坐标是易腐读数，跨不过一次求值；能跨页传递的定位要用序号，不用像素。**
